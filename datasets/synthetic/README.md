# Synthetic Trajectories — Annotation Guidelines

This directory contains hand-crafted agent trajectories used for benchmarking failure detection systems. Each trajectory is a JSON file with a structured format that maps directly to the ATFD schema.

## Directory Structure

```
synthetic/
├── README.md               — This file
└── trajectories/           — Individual trajectory JSON files
    ├── tool_loop_001.json
    ├── hallucination_001.json
    └── ...
```

## Trajectory JSON Format

Each trajectory file must contain the following top-level fields:

| Field | Type | Description |
|---|---|---|
| `trajectory_id` | string | Unique identifier, prefixed with `synth_` |
| `domain` | string | Business domain (e.g. `retail`, `legal`, `hr`) |
| `description` | string | One-sentence summary of the failure scenario |
| `ground_truth` | object | Label with `outcome`, `failure_categories`, `quality_categories` |
| `failure_event_indices` | list[int] | Zero-based indices of events that exhibit the failure |
| `events` | list[object] | Ordered list of conversation events |

### Ground Truth

```json
{
  "outcome": "fail",
  "failure_categories": ["process.tool_loop"],
  "quality_categories": []
}
```

- `outcome`: one of `"pass"`, `"degraded"`, `"fail"`
- `failure_categories`: list of taxonomy codes (see below)
- `quality_categories`: list of quality taxonomy codes (empty for failure-only trajectories)

### Event Format

```json
{"type": "system", "content": "..."}
{"type": "user_message", "content": "..."}
{"type": "assistant_message", "content": "..."}
{"type": "tool_call", "content": "<tool_name>", "metadata": {"tool_name": "...", "args": {}}}
{"type": "tool_result", "content": "<json_string>"}
```

Timestamps are auto-generated by the `SyntheticAdapter` at load time (not stored in JSON).

## Failure Taxonomy Codes

Use dot-separated codes from the ATFD taxonomy. Common codes:

| Code | Description |
|---|---|
| `process.tool_loop` | Agent calls the same tool repeatedly without progress |
| `process.infinite_loop` | Agent enters a loop that never terminates |
| `communication.hallucination` | Agent fabricates facts not in context or tools |
| `communication.missing_info` | Agent fails to convey required information |
| `action.wrong_tool` | Agent uses the wrong tool for the task |
| `action.wrong_args` | Agent calls a tool with incorrect arguments |
| `state.wrong_state` | Agent leaves the system in an incorrect state |
| `infrastructure.max_steps` | Agent exceeded the maximum allowed steps |

## Annotation Rules

1. **One failure per file** — Each trajectory should illustrate a single, clear failure mode. Multi-failure trajectories are allowed but must have all categories listed.

2. **Minimal context** — Include only as many events as needed to make the failure evident. Avoid padding with irrelevant turns.

3. **Realistic content** — System prompts, user messages, and tool results should reflect plausible production scenarios for the stated domain.

4. **failure_event_indices** — Mark the specific event indices (zero-based) where the failure manifests, not the entire trajectory. For tool loops, mark each repeated redundant call.

5. **Trajectory IDs** — Use the pattern `synth_<category_short>_<NNN>` (e.g. `synth_tool_loop_001`, `synth_hallucination_001`). File names must match the trajectory ID with `.json` extension.

6. **No timestamps in JSON** — Timestamps are generated automatically by the adapter. Do not include a `timestamp` field in event objects.

## Consensus

All synthetic trajectories are assigned `"gold"` consensus by the adapter because they are hand-crafted with full annotator control. Disputed or majority-consensus trajectories should not be added to the synthetic set — use the tau-bench or crowd-sourced datasets for those.

## Adding New Trajectories

1. Choose a failure category from the taxonomy.
2. Draft a realistic multi-turn conversation that clearly exhibits the failure.
3. Mark `failure_event_indices` carefully — reviewers will use these to assess localization.
4. Place the file in `trajectories/` with a unique `synth_*` ID.
5. Run `pytest tests/test_converters.py` to verify the adapter loads the new file without errors.
